# Spec: AI 프롬프트에 자가 점검 목록·반영 결과 확인 단계 추가
- Intent: [INT-010](intent.md) | Status: planned | 작성일: 2026-11-18
- Intent updated_at: 2026-11-17T23:54:18+09:00

## 1. 개요
- 원 요구: google-gemini/demolab(Apache-2.0, 스킬 1개 `skills/gemini-frontend-design/SKILL.md`)을 검토한 뒤 "생성 프롬프트 끝에 사전 점검 체크리스트 + 브라우저 도구 존재 시 재캡처 시각 확인, 없으면 폴백" 기법을 채택했다(선택 A, 출처: 대화 요청).
- 문제: 익스텐션 `AI 프롬프트 복사`가 만드는 프롬프트(`buildPrompt`, INT-006 done)는 위치와 변경값만 전달한다. 그래서 구현 에이전트가 과잉 수정이나 누락을 스스로 검출할 기준이 없다.
- 해결: `buildPrompt` 출력 말미에 두 섹션을 추가한다. 두 모드('내역 전체'/'선택 요소')에 모두 적용한다.
  1. `## 자가 점검`: 수치로 검증할 수 있는 체크 목록이다.
  2. `## 반영 확인`: 브라우저 확인 도구가 있으면 별도 브라우저에서 비교하고, 없으면 새로고침 후 수동 확인으로 폴백한다. 예시로 chrome-devtools-mcp를 병기한다.
- 인계: 새 세션은 이 문서와 `plan.md`만으로 착수할 수 있다(§9 모의 독해 참조). intent의 미해결 질문 1건은 `[x]`로 확정됐다.

## 2. 범위 (In-scope / Out-of-scope)
- In-scope
  - `packages/extension/src/prompt.ts`: `changesPrompt`·`selectionPrompt` 말미에 두 섹션을 붙인다. 섹션 문구를 만드는 순수 헬퍼를 추가한다.
  - `packages/extension/test/prompt.test.ts`: 새 섹션을 검증하는 테스트를 추가하고, 필요하면 기존 단언을 갱신한다.
- Out-of-scope (intent 범위 밖·전제)
  - 디자인 생성 규칙 도입(demolab 스킬 원문 복사 포함, D-02).
  - 서버·MCP 도구 계약·플러그인 변경.
  - INT-008 인라인 값 해제 구현.
  - 스킬 패키징·멀티 호스트 매니페스트(INT-003 참고용), 디자인 안티패턴 기반 CSS 편집 경고(D-01 폐기 대안).
  - 브라우저 도구 존재 여부의 런타임 감지. `prompt.ts`는 순수 함수라 감지할 수 없으므로 "있으면 A, 없으면 B" 정적 문구로 적는다.
  - `README.md` 수정. intent 제안 결과에 없으므로 이번 범위에 넣지 않는다(§9 R-3).

## 4. 기능 요구사항 (FR-n)
- FR-1 내역 모드 자가 점검: `changes`가 1건 이상이면 항목 루프 뒤에 빈 줄과 `## 자가 점검` 섹션을 붙인다. 체크 항목은 `- [ ] ` 접두를 쓰고, 다음을 포함한다.
  - 수정한 선언이 위 항목 N개(실제 개수)의 속성뿐이다. 다른 속성·요소 변경 0건.
  - 각 항목의 변경값이 `after` 값과 일치한다.
  - 요청과 무관한 파일·포맷·네이밍 diff 0건(`git diff`로 확인).
- FR-2 선택 모드 자가 점검: `selectionPrompt` 말미에 빈 줄과 `## 자가 점검` 섹션을 붙인다. `after`가 없으므로 다음을 포함한다.
  - 위 위치(선택 요소)에 해당하는 코드만 수정했다.
  - 요청과 무관한 파일·포맷·네이밍 diff 0건.
- FR-3 내역 모드 반영 확인: 자가 점검 뒤에 빈 줄과 `## 반영 확인` 섹션을 붙인다.
  - 브라우저 확인 도구가 있으면(예: chrome-devtools-mcp): DOMirror 익스텐션이 없는 별도 브라우저에서 위 페이지 URL을 열거나 새로고침한다. 각 항목 요소의 계산값을 `after`와 비교하고 불일치 항목을 보고한다.
  - 같은 탭 비교 금지 이유 1줄: 편집한 탭에는 보낸 값이 인라인 `!important`로 남아 반영에 실패해도 일치로 보인다(`README.md:177`).
  - 도구가 없으면: 사용자에게 페이지를 새로고침해 각 항목을 직접 확인하도록 안내한다.
- FR-4 선택 모드 반영 확인: 같은 섹션 구조를 쓰되 비교 대상은 "요청한 변경"이다(`after` 없음). 도구가 있으면 별도 브라우저에서 위 페이지 URL을 다시 열어 화면을 확인하고, 없으면 새로고침 후 수동 확인을 안내한다.
- FR-5 빈 내역: `changes`가 0건이면 두 섹션을 붙이지 않는다. 머리만 돌려주는 기존 동작(`prompt.ts:107`)을 유지한다(D-S1).
- FR-6 단위 테스트: `prompt.test.ts`에 FR-1~FR-5를 검증하는 테스트를 추가한다. 기존 테스트는 전부 통과해야 한다.

## 6. 인터페이스 · 데이터 스키마
- 확정: `buildPrompt(input: PromptInput): string` 시그니처와 `PromptInput`·`PromptSelection` 타입은 바뀌지 않는다. 호출처(`content.ts:287`) 변경 0건.
- 초안(헬퍼 이름·문구 세부는 구현 시 조정 가능, 의미·헤더는 고정)
```ts
// prompt.ts (모듈 내부, export 불필요)
function changesFooter(count: number): string[];   // FR-1·FR-3, '' 구분 줄 포함
function selectionFooter(): string[];              // FR-2·FR-4
```
- 출력 예(내역 모드, 2건)
```markdown
## 자가 점검
- [ ] 위 2개 항목의 속성만 수정했다(다른 속성·요소 변경 0건).
- [ ] 각 항목의 변경값이 `after` 값과 일치한다.
- [ ] 요청과 무관한 파일·포맷·네이밍 diff가 0건이다(`git diff`로 확인).

## 반영 확인
- 브라우저 확인 도구가 있으면(예: chrome-devtools-mcp): DOMirror 익스텐션이 없는 별도 브라우저에서 위 페이지 URL을 새로 열고, 각 항목 요소의 계산값을 `after`와 비교해 불일치 항목을 보고한다.
- 편집한 탭에는 보낸 값이 인라인 `!important`로 남아 있어 같은 탭 비교는 반영 실패도 일치로 보인다.
- 도구가 없으면: 사용자에게 페이지를 새로고침해 각 항목이 바뀌었는지 직접 확인하도록 안내한다.
```
  - 항목 수 N은 `changes.length`로 채운다(중복 key 처리는 기존 루프 기준과 같게 한다).
  - 색·단위 표기 차이(`#fff`↔`rgb()`)는 구현 시 "정규화 후 비교" 한 구절을 넣을 수 있다. 의미 변경이 아니므로 재승인 불필요.

## 7. 예외 · 엣지 케이스
- E-1 빈 내역: 섹션을 붙이지 않는다(FR-5). `:194` 계열 테스트와 `:197`~`:198` 단언이 그대로 통과한다.
- E-2 페이지 URL 여러 종(`:86`): 반영 확인은 URL을 다시 적지 않고 "위 페이지 URL"로 참조한다. 그래서 `- 페이지: ` 개수 단언(`:109`·`:117`)이 바뀌지 않는다(D-S3).
- E-3 stale 항목(`:85`): 자가 점검 문구는 바꾸지 않는다. stale 주의는 항목 줄에 이미 있다.
- E-4 선택 모드 위치 미확인(`located: null`): 자가 점검의 "위 위치"는 위치가 없을 때도 의미가 통하도록 "선택한 요소에 해당하는 코드"로 적는다. `- 위치: ` 접두는 쓰지 않는다.
- E-5 브라우저 도구 유무: 프롬프트가 감지하지 않는다. 판단은 받는 에이전트가 한다(정적 분기 문구).
- E-6 마크다운 체크박스를 지원하지 않는 에이전트: `- [ ] ` 텍스트로도 읽히므로 문제없다.
